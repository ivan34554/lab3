# Lab 3. Подкасты: база данных и бизнес-операции (вариант 12)

Лабораторная работа по дисциплине «Разработка безопасного программного обеспечения».
REST API для системы публикации подкастов из Лабы 2, переведённый с хранения в памяти на PostgreSQL.
Поверх CRUD добавлены бизнес-операции планирования и публикации выпусков.

## Назначение

Автор заводит подкаст, добавляет в него эпизоды и аудиофайлы, планирует публикацию выпуска на
определённое время и публикует его. Сервис следит за тем, чтобы данные оставались согласованными:
нельзя опубликовать эпизод без основного аудиофайла, нельзя планировать выпуски в архивном подкасте,
у эпизода не бывает двух основных файлов и т.п.

## Стек

- Java 21, Spring Boot 4.1.1 (Spring MVC, Spring Data JPA / Hibernate), Bean Validation, Lombok
- PostgreSQL 16 (в Docker), драйвер `org.postgresql:postgresql`
- Maven (`mvnw`)

## Предметная модель

```
users 1 ──< podcasts 1 ──< episodes 1 ──< audio_files
                │               └─────────< publication_slots >── podcasts
```

| Сущность | Таблица | Путь API | Основные поля |
|---|---|---|---|
| Пользователь | `users` | `/api/users` | `username`, `email` (уникальны без учёта регистра) |
| Подкаст | `podcasts` | `/api/podcasts` | `title`, `authorId`, `status` (`ACTIVE`, `ARCHIVED`) |
| Эпизод | `episodes` | `/api/episodes` | `podcastId`, `title`, `durationSeconds`, `state` (`DRAFT`, `SCHEDULED`, `PUBLISHED`) |
| Аудиофайл | `audio_files` | `/api/audio-files` | `episodeId`, `path`, `format`, `sizeBytes`, `main` |
| Публикационный слот | `publication_slots` | `/api/publication-slots` | `podcastId`, `episodeId`, `scheduledAt`, `status` (`PLANNED`, `PUBLISHED`, `CANCELLED`), `publishedAt` |

### Ограничения целостности (в схеме БД, `db/init/02-schema.sql`)

- внешние ключи с `ON DELETE CASCADE`: удаление пользователя удаляет его подкасты, подкаста - эпизоды и слоты,
  эпизода - файлы и слоты, без висячих ссылок;
- эпизод в слоте обязан принадлежать подкасту слота (составной внешний ключ `(episode_id, podcast_id)`);
- у эпизода не больше одного основного аудиофайла (частичный уникальный индекс по `is_main`);
- у эпизода не больше одного запланированного и не больше одного опубликованного слота;
- `published_at` заполнено тогда и только тогда, когда слот `PUBLISHED`;
- `CHECK`: допустимые значения статусов и форматов, положительные длительность и размер, непустые названия,
  безопасный относительный путь файла (без `..` и ведущего `/`);
- уникальны: имя и e-mail пользователя, путь файла в пределах эпизода.

### Пользователь БД с ограниченными правами

Приложение подключается не владельцем БД, а пользователем `podcast_app`. Он состоит в групповой роли
`podcast_readwrite`, у которой есть только `SELECT`, `INSERT`, `UPDATE`, `DELETE` на таблицы и `USAGE` на
последовательности. Менять структуру БД (`CREATE`, `DROP`, `ALTER`) и делать `TRUNCATE` он не может.
Схему создаёт владелец БД `podcast_owner` при инициализации контейнера, Hibernate только проверяет её
(`ddl-auto=validate`).

## Бизнес-операции

CRUD-операции (`GET`, `POST`, `PATCH`, `DELETE` по каждой сущности) работают как в Лабе 2, но через БД.
Состояния (`state`, `status`, `main`) через `PATCH` не меняются: они меняются только операциями ниже,
иначе можно было бы обойти правила. Создание слота (`POST /api/publication-slots`) - это планирование
публикации и тоже следит за состоянием эпизода.

| Операция | Запрос | Что делает | Когда недопустима (409) |
|---|---|---|---|
| Запланировать публикацию | `POST /api/publication-slots` | создаёт слот `PLANNED`, эпизод `DRAFT` → `SCHEDULED` | подкаст в архиве; эпизод не `DRAFT` (уже запланирован или опубликован); (400, если время не в будущем или эпизод чужого подкаста) |
| Опубликовать слот | `POST /api/publication-slots/{id}/publish` | слот → `PUBLISHED`, эпизод → `PUBLISHED` | слот не `PLANNED`; время слота ещё не наступило; у эпизода нет основного файла; подкаст в архиве |
| Отменить слот | `POST /api/publication-slots/{id}/cancel` | слот → `CANCELLED`, эпизод `SCHEDULED` → `DRAFT` | слот не `PLANNED` |
| Опубликовать эпизод сейчас | `POST /api/episodes/{id}/publish-now` | публикует эпизод немедленно: запланированный слот досрочно либо новый слот, эпизод → `PUBLISHED` | эпизод уже опубликован; нет основного файла; подкаст в архиве |
| Назначить основной файл | `POST /api/audio-files/{id}/make-main` | файл становится основным, прежний основной перестаёт им быть (в одной транзакции) | эпизод опубликован; файл уже основной |
| Архивировать подкаст | `POST /api/podcasts/{id}/archive` | подкаст → `ARCHIVED`, запланированные слоты → `CANCELLED`, `SCHEDULED`-эпизоды → `DRAFT`; в ответе число отменённых слотов и возвращённых эпизодов | подкаст уже в архиве |
| Восстановить подкаст | `POST /api/podcasts/{id}/restore` | подкаст → `ACTIVE` | подкаст не в архиве |

Операции затрагивают несколько сущностей одновременно (слот и эпизод; эпизод и слот и файлы; подкаст, слоты и
эпизоды; файл и эпизод), а результат зависит от текущего состояния связанных объектов: времени слота,
наличия основного файла, статуса подкаста.

Дополнительные правила состояния:

- файлы опубликованного эпизода менять, добавлять и назначать основными нельзя; основной файл
  запланированного эпизода удалить нельзя;
- опубликованный слот нельзя изменить и удалить; перенести время можно только у `PLANNED`-слота;
- эпизоды в архивном подкасте создавать нельзя;
- время (`createdAt`, `publishedAt`) задаёт сервер по единому `Clock`, из запросов оно не принимается.

### Как обеспечивается согласованность

- каждая операция выполняется в одной транзакции (`@Transactional`): либо все изменения, либо ни одного;
- конкурирующие запросы сериализуются пессимистическими блокировками строк (`SELECT ... FOR UPDATE / FOR SHARE`)
  в едином порядке: подкаст → эпизод. Два одновременных `publish` одного слота не могут оба выполниться;
- последняя линия защиты - ограничения БД: если гонка всё же нарушит инвариант, база отклонит изменение,
  а API ответит `409`.

### Коды ответов

`400` - неверные данные или ссылка на несуществующий объект в теле запроса; `404` - объект из пути не найден;
`409` - операция недопустима в текущем состоянии данных или нарушает ограничение БД;
`500` - внутренняя ошибка без подробностей (детали пишутся только в лог).

```json
{"status": 409, "message": "Slot time has not come yet"}
```

## Запуск

Нужны Docker Desktop и Java 21.

Быстрый вариант: двойной щелчок по `start.command` в Finder (или `./start.command` в терминале). Он запускает
Docker и БД, прогоняет тесты и стартует приложение. То же самое по шагам:

```bash
# 1. Секреты: скопировать шаблон и задать свои пароли (.env в git не попадает)
cp .env.example .env

# 2. База данных (создаёт БД, роли, схему и тестовые данные при первом запуске)
docker compose up -d

# 3. Приложение на http://localhost:8080
./mvnw spring-boot:run
```

Пароли (`DB_PASSWORD`, `DB_OWNER_PASSWORD`) задаются в `.env`; приложение читает их оттуда
(`spring.config.import`), а переменные окружения с теми же именами имеют приоритет.
Если нужно пересоздать БД с нуля: `docker compose down -v && docker compose up -d`.

Тесты (нужна запущенная БД, данные после тестов не остаются): `./mvnw test`.

### Тестовые данные

При первом запуске БД заполняется (`db/init/03-seed.sql`): 3 пользователя, 3 подкаста (один в архиве),
7 эпизодов во всех состояниях, аудиофайлы и слоты. Сбросить данные к исходным:

```bash
docker compose exec -T db psql -U podcast_owner -d podcasts < db/init/03-seed.sql
```

Что есть в тестовых данных для проверки операций: эпизод 2 запланирован (слот 2), эпизод 3 имеет два файла
без основного (файлы 3 и 4), эпизод 5 готов к `publish-now`, эпизод 4 без аудио (операция вернёт `409`),
подкаст 3 в архиве.

## Коллекция запросов

`postman/lab3.postman_collection.json` - коллекция Postman (импорт: *Import* → выбрать файл).

1. Папка «Сценарий: бизнес-операции» воспроизводит осмысленный сценарий: создать пользователя, подкаст,
   эпизод и файлы → попытаться опубликовать без основного файла (`409`) → назначить основной файл →
   запланировать публикацию → попытки опубликовать раньше времени и повторно запланировать (`409`) →
   отменить слот → запланировать заново → опубликовать досрочно → проверить заморозку файлов →
   запланировать второй эпизод → архивировать подкаст (слот отменён, эпизод вернулся в черновик) →
   восстановить подкаст.
2. Папка «CRUD по каждой сущности» проходит `GET` (список и по id), `PATCH`, `DELETE` для всех пяти сущностей,
   проверки валидации (`400`), уникальности (`409`) и каскадного удаления (`404` после удаления подкаста).

Запускать папки целиком, по порядку (*Run collection*): запросы передают друг другу идентификаторы через
переменные коллекции, в каждом запросе есть проверки кодов и состояний. Быстрая проверка без Postman:
`./scripts/smoke.sh`.

```
src/main/java/com/example/lab3/

  service/          бизнес-логика, транзакции, блокировки

  model/            JPA-сущности
  dto/ exception/ config/
```
